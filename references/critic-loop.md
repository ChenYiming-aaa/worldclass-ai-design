# 设计评审循环（技术 3）细则

原理见 `SKILL.md` 反直觉事实 3；verbatim prompt 与评分标准三档见 `references/prompts.md` 技术 3；故障排查集中在 `references/edges-and-failures.md`。本文件只讲纪律与停止条件。

## 每轮的执行顺序

1. 执行 Agent 完成当前版本 → **截图**
2. 在**全新上下文**中调用 Critic，**只给截图**
   - 不给代码
   - 不给实现细节
   - 不给早期迭代
   - 不给上一轮的评审意见与辩解
3. Critic 输出：
   - 判断这个设计在追求什么审美
   - 想象顶级设计工作室会如何执行同一审美
   - 列出最大的差距（biggest gaps）
   - 给出 /10 的分数
4. 执行 Agent 按优先级修改 → 回到第 1 步

## 必须遵守的纪律

| 纪律 | 原因 |
|---|---|
| **Critic 在全新上下文中启动** | 一旦看到代码和历史，它就会重蹈执行 Agent 的主观陷阱 |
| **只给截图** | 强制它像用户一样看结果，而不是像工程师一样看实现 |
| **每轮用同一个 Critic prompt** | 评分才具有跨轮可比性；换 prompt = 换尺子 |
| **9/10 门槛不写进 Critic prompt** | 否则 Critic 为了让流程结束而放水，评分失去客观性 |
| **反馈要 tight & specific，不要 vague prose** | 含糊的反馈无法被执行 |
| **Critic 要 bold & opinionated** | 依赖 safe / easy 的判断等于退回平均值 |
| **惩罚 overdone / excessive / 明显 AI 生成的模式** | 这是本流程的核心目标之一 |
| **既看整体结构与构图，也看细节** | 只顾一头会漏掉另一类问题 |

## 停止条件（最容易失控的一环）

**不要无限跑。** Critic 可能永远觉得设计不够好，Agent 会无助地烧 token 去讨好它。

1. 先 prompt 它做 **1–2 轮**，看反馈与评分是否收敛。
2. 如果**连续两轮意见反复、评分不升** → 停止循环，**由人调整方向**，而不是让代理继续消耗。
3. 若确需继续，再逐步增加轮次，但仍设硬上限。

## 模型分配

- **Critic**：用更大、能力更强的模型。它只做高层决策，调用频次低，用贵模型不会破产。
- **Implementer**：用更快更便宜的模型做执行苦力，但**不要太小**——它仍需能很好地执行设计方向。

## 参考图

可以给 Critic 看你喜欢的设计或概念图来展示质量门槛，但必须在 prompt 里写明它们是 **baseline / moodboard，不是 target**，否则 Critic 会照抄。可用的 "Great" 档写法见 `prompts.md` 技术 3。

## 无法截图时的降级方案

- 把渲染结果贴到**另一个独立会话**里请它评审——效果弱于看图，但保留了"独立上下文"这个最关键的属性。
- 直接跳过技术 3，把精力放在技术 1、2、6 上（这三者在纯聊天环境里同样有效）。
